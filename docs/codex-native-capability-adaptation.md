# Codex 原生能力适配需求汇总

整理日期：2026-10-04

源码基线：`695eb0ca6f2ed841309f17a00a2dbb090fcf234a`

文档状态：Steer 修复进行中；其余功能仍为需求汇总与初步技术评估。

## 1. 目标与范围

在 Agents Anywhere 现有架构上补齐常用 Codex 原生能力，使 Windows、Web 和 Android 能正确发起操作、展示过程并回传用户输入。

涉及的实现层包括：

- Windows 客户端：`desktop-workbench`。
- Web 客户端：`web-next`。
- Android 客户端：`android`。
- 共用服务端：`server`。
- Connector 中的 Codex 适配层：`connector/connector/runtimes/codex`。

现有项目已经具备会话管理、运行时能力声明、命令菜单、交互请求、远程文件访问和事件同步框架，可以在此基础上扩展。整体属于中等偏大的适配工程；下文难度是相对评估，不是工期承诺。

“已确认”表示已核对当前源码；“待定位”表示用户已反馈现象，但尚未用具体失败请求复现并确认根因。官方接口存在不等于项目已接入，也不保证所有已安装的 Codex 版本都支持，实施时应验证实际运行版本。

## 3. 各项需求与验收目标

### 3.1 Steer：运行中追加指令

当前 Connector 已实现 `steer_turn`，服务端也有对应入口。三端输入框的发送条件均排除了运行中状态，停止按钮同时占用了发送入口。Android 虽已有普通发送与 steer 的分流，点击和键盘发送仍被 `canSend` 拦截；这是已确认的源码缺陷，不再列为待定位。

需要适配：

- 根据服务端提供的实际能力开放运行中输入，将追加指令发送给正在执行的 turn。
- 保留用户输入及提交状态，正确展示已接受、失败和可重试结果，避免重复显示消息。
- 处理提交瞬间 turn 已结束、正在停止、等待审批、连接断开等状态；明确提示追加是否成功。
- 区分“本轮追加指令”和“排队到下一轮”的行为，重试不能悄悄改变用户原本选择的操作。

验收：三端在可 steer 的运行状态下均可提交追加指令；追加不会意外创建另一轮或先停止当前轮；失败不会丢失用户输入，切换会话或重连后结果仍然一致。

### 3.2 选择菜单／交互提问

用户反馈：Codex 有时返回带选项的提问，前端却显示为普通消息，无法点击回答。源码中已经存在 `input_request` 表单模型及部分答案构造逻辑，因此应先定位具体缺口，不能把整个交互请求功能认定为未实现。

首先核对失败样本属于哪种情况：

- 原生结构化交互请求：检查原始请求、请求 ID、问题与选项字段、Connector 映射、服务端通知以及客户端渲染。
- 普通文本回复中的选项列表：它本身未必对应正在等待答案的原生请求。若需要快捷回复按钮，应作为独立交互体验处理，不能伪造原生请求 ID。

需要适配：

- 对原生提问展示其协议实际支持的选项、多个问题和自由文本输入；是否支持多选应以原始协议为准。
- 将答案关联到准确的会话、请求和问题，并通过交互回复通道提交。
- 展示等待回答、提交中、已提交、失败、已取消或失效状态。
- 保留未提交的填写内容；重连后恢复仍有效的请求，并同步另一端已提交的结果。

验收：完成一次原生交互提问的“收到请求 → 选择或填写 → 提交 → Codex 继续执行”全过程；重复提交、过期请求和跨端回答不会导致误提交或永久等待。

### 3.3 计划模式

官方 App Server 提供 `collaborationMode`。当前项目的启动 turn 参数未接入该字段，`PlanThreadItem` 则被转为普通系统消息。

需要适配：

- 提供计划模式切换入口，将原生模式参数传到 Codex，并显示实际生效的模式。
- 保存并同步会话模式，处理切换会话、客户端重启及其他客户端修改模式的情况。
- 正确展示流式计划、最终计划及计划过程中提出的结构化问题。
- 提供从计划进入执行的明确操作，遵循当前 Codex 版本的模式切换限制。
- 区分“原生计划模式”和普通执行过程中显示的任务步骤列表。

验收：三端切换后原生模式确实生效；计划可正常阅读和回答问题，用户确认进入执行后状态正确转换；仅发送“请先做计划”文字不能算完成原生模式适配。

### 3.4 Goal 模式

官方已提供 `thread/goal/set`、`thread/goal/get`、`thread/goal/clear`，本机 SDK 中也有对应类型。当前项目尚未接入这些能力。

需要适配：

- 设置、查看和编辑目标，并支持原生协议提供的暂停、恢复、清除操作。
- 展示目标状态及协议提供的预算、消耗和进度信息，不把暂时没有消息误判为完成。
- 同步 `thread/goal/updated`、`thread/goal/cleared` 等事件；重连后重新读取原生目标状态。
- 明确目标暂停、单轮中断、连接断开和目标完成之间的区别。

验收：目标与正确的原生 thread 绑定；跨端查看、暂停恢复和客户端重连后状态一致，预算与状态展示对应原生数据；不会因客户端重复提交而意外重置目标或使用记录。

### 3.5 `/` 命令

当前已有命令菜单、命令列表与执行协议，但 Codex 的命令列表实现返回空，执行入口统一返回 `unknown_command`。适配应为每个命令定义明确行为。

首批候选命令与映射方向：

| 命令 | 产品行为 |
| --- | --- |
| `/model` | 打开模型及推理强度选择，并同步实际设置 |
| `/plan` | 切换原生计划模式；包含行内提示词时按原生约定处理 |
| `/compact` | 调用已有原生压缩能力，并展示执行状态 |
| `/skills` | 打开当前会话可用的技能选择器 |
| `/mention` | 打开当前工作目录的文件引用选择器 |
| `/goal` | 在 Goal 适配完成后接入目标管理 |

这些是建议范围，实施时应对照所支持 Codex 版本的命令集确认。命令本身可能是客户端界面操作、原生 API 操作或需要额外交互的流程；原样发送 `/命令` 文本不能替代对应功能。

需要具备补全、参数校验、执行状态、禁用原因和未知命令反馈。对于 CLI 专有的终端或本机界面命令，应明确标记支持、等效实现或不适用，逐项跟踪“所有命令”的覆盖情况。

验收：首批命令从输入、选择到生效均可完成；运行中命令的即时执行、排队或暂不可用行为明确；跨端菜单与实际运行时能力一致。

### 3.6 Skill 选择与调用

技能应从会话所属 Connector 所在电脑、对应工作目录获取。当前缺少显式技能选择与结构化发送链路，不等于原生 Codex 的技能自动发现完全失效。

需要适配：

- 调用 `skills/list` 获取当前工作目录可用的技能，显示名称、描述、可用状态及必要的来源信息。
- 支持搜索、选择、取消选择和消息回显；目录或技能发生变化后刷新列表。
- 按官方协议传递 `skill` 输入。官方显式引用使用 `$技能名`；产品也可提供 `@` 选择界面，再转换为正确请求。
- 在持久化和重试过程中保留技能身份与路径，处理技能消失或不可用的情况。

验收：选择的技能可追踪到对应 Connector 的实际技能，并以正确的原生输入发送；同名技能不会被错误替换，消息回显与重试保持一致。

### 3.7 `@` 文件与目录引用

项目已有远程文件浏览和插入 `@路径` 的能力，需进一步补齐输入框内的搜索补全与引用处理。引用指向会话所在电脑的路径，不是手机自身的文件系统。

需要适配：

- 按当前工作目录搜索文件或目录，支持键盘和触屏选择，并显示足够的路径信息用于区分同名项。
- 处理相对路径、绝对路径、Windows 盘符、中文、空格及路径分隔符。
- 明确引用的发送语义：引用路径、上传附件和读取内容分别是什么行为，目录引用不应默认递归上传全部文件。
- 保留引用信息用于回显与重试，处理目标移动、不存在或权限不足的情况。

验收：三端可选择文件和目录并提交有效引用；中文与含空格的 Windows 路径可正确解析；不会把手机本地路径误当成远程工作目录路径。

### 3.8 原生事件展示

已发现 `SleepThreadItem` 会走未识别类型的降级路径，生成 `kind: "unknown"` 与 `rawType`，前端因而显示 `unknown`，原生等待时长等信息未被保留。该事件表示等待，单凭它不能认定会话执行失败。

需要适配：

- 在 Connector 中统一映射等待、计划、目标、交互请求等本次功能涉及的原生事件。
- 保留事件 ID、关联对象、原生状态、时长等展示和恢复所需字段。
- 三端用共同语义展示事件，避免各端分别猜测原始类型。
- 对未来未知类型保留可诊断信息并提供合理降级；不将未知事件自动视为错误或可点击操作。

验收：已支持事件有可理解的名称与正确状态；未知事件不会破坏时间线，必要信息可用于后续定位；等待、完成、失败与等待用户回答可以区分。

## 4. 共用实现要求

| 层级 | 主要职责 |
| --- | --- |
| Codex 适配层 | 调用原生接口、转换结构化输入、映射事件并提供真实能力状态 |
| Connector 与服务端协议 | 传递模式、目标、引用及交互数据，保留请求关联标识并定义兼容策略 |
| 服务端 | 提供统一入口、校验请求、同步状态，并支持快照读取与断线恢复 |
| Windows／Web／Android | 呈现可用功能，保存未提交输入，发送操作并根据实际结果更新界面 |

实施前应核对当前 runtime-control 契约和生成类型，优先复用已有命令、能力、交互及文件接口。需要新增字段时，应同步更新协议定义、服务端模型、Connector 和客户端类型。

所有功能共同要求：

- 依据实际运行时版本、会话状态和能力声明开放功能，给出不可用原因。
- 同时覆盖首次快照、实时事件、切换会话和重连恢复，避免必须离开会话再回来才能刷新。
- 为操作保留关联 ID 并处理重复请求、迟到响应和多客户端并发操作。
- 验证新旧客户端、服务端与 Connector 的兼容行为，明确需要一起升级的组件。
- 保持模型、权限、消息、停止会话及其他运行时的既有行为可用。

## 5. 建议实施顺序

1. **第一阶段：Steer 与选择菜单。** 修复运行中输入入口，定位具体选择菜单失败样本，打通原生提问到答案回传；同步补齐相关事件和状态恢复。
2. **第二阶段：计划模式与首批 `/` 命令。** 接入原生计划参数和展示，利用已有命令框架补模型、计划、压缩等操作。
3. **第三阶段：Skill 与文件／目录引用。** 完善输入结构、目录查询、选择器、路径处理和回显，并补 `/skills`、`/mention`。
4. **第四阶段：Goal 模式。** 接入目标状态、控制、预算和恢复，并补 `/goal`。

原生事件适配贯穿各阶段。以上是建议顺序，未承诺工期；Steer 已定位并开始修复，选择菜单仍需具体失败样本。

## 6. 综合验收清单

- [ ] 三端均能在受支持的运行状态下 steer，并正确回显成功与失败。
- [ ] 原生交互提问能选择、填写、提交，Codex 收到正确答案后继续执行。
- [ ] 交互请求在切换会话、断线及跨端回答后状态一致。
- [ ] 原生计划模式参数生效，计划展示和后续执行流程完整。
- [ ] Goal 的设置、编辑、暂停、恢复、清除及预算状态与原生 thread 一致。
- [ ] 首批 `/` 命令有明确行为、错误反馈和可用状态；其余命令有覆盖记录。
- [ ] Skill 来自正确的 Connector 和工作目录，并以正确结构发送。
- [ ] 文件和目录引用支持 Windows 中文、空格及不同路径形式。
- [ ] 已适配事件不再无故显示 `unknown`，未知事件仍可安全展示和诊断。
- [ ] 关键状态无需切换会话即可更新，重连后能够恢复。
- [ ] 重复提交、失败重试和版本不兼容时不会丢失输入或静默改变操作语义。
